# 轻析 LiteOps：轻量化数据运营提效工作台 PRD

> 补齐 BI 看板之外的长尾数据工作流——从取数、清洗到分析报告产出与知识沉淀的一体化轻量工具

- **文档版本**：V1.0（Vibe Coding 开发基线）
- **文档状态**：需求评审稿
- **产品形态**：本地优先 Web 应用 / 轻量私有化部署
- **目标用户**：数据运营 / 数据分析师 / 运营岗
- **编写日期**：2026-09-03

## 1. 项目背景

### 1.1 产品定位

轻析 LiteOps 是一款面向数据运营/分析从业者的轻量化提效工作台，定位为 **"BI 工具能力边界之外的数据需求承接器"**：不做常态化看板和指标可视化（这是 Tableau / Power BI / 帆软等 BI 工具的主场），而是把 BI 覆盖不到的**临时性、长尾型、非标准化**数据工作——找数、取数、洗数、做分析、写报告、沉淀复用——收敛到一个轻量工具中，配合 AI Agent 完成"需求进、报告出"的闭环。

**一句话定位**：BI 解决"每天看同一批数"的问题；轻析解决"每天都有新的临时数据需求，且 80% 的时间耗在找数、洗数和写报告上"的问题。

### 1.2 与 BI 工具的能力边界

| 工作环节 | BI 工具（Tableau / Power BI 等） | 轻析 LiteOps（本产品） |
| --- | --- | --- |
| 常态化监控 | ✅ 核心看板、指标大屏、定时刷新 | ❌ 不做（明确边界） |
| 临时取数 | ⚠️ 依赖已建模的数据仓库，新需求需排期开发 | ✅ 本地文件/数据库直连导入，即导即用 |
| 数据清洗 | ❌ 基本不支持，需依赖上游 ETL | ✅ 自动体检 + 可配置清洗流程 + 变更统计 |
| 探索性分析 | ⚠️ 拖拽图表为主，分析过程不沉淀 | ✅ 分析框架模板引导 + SQL 片段复用 |
| 报告产出 | ❌ 不产出文字报告 | ✅ AI 辅助搭框架、精炼语言，导出 Word/PDF |
| 知识沉淀 | ❌ SQL、口径、方法散落在个人电脑/聊天记录 | ✅ SQL 片段库 + 学习文档库统一沉淀检索 |
| 需求管理 | ❌ 无 | ✅ 需求 List 录入 + 紧急性排序 |

### 1.3 目标用户

- **主：数据运营 / 数据分析师**：1-3 年经验，日常承接业务方临时数据需求，Excel/SQL 熟练，是本产品的核心用户与主要操作人。
- **次：产品运营 / 业务运营**：有数据意识但 SQL 基础弱，需要自助完成轻度取数、清洗和报告框架搭建，减少对数据团队的排队依赖。
- **团：小团队负责人 / 数据 BP**：3-10 人数据小组，需要统一沉淀 SQL 资产与分析方法、管理需求优先级，避免重复劳动。

### 1.4 业务目标（可量化）

| 目标 | 基线（现状） | V1.0 目标 | 度量方式 |
| --- | --- | --- | --- |
| 单次临时数据需求的数据准备耗时 | 找数+清洗约占全流程 50%-60% 时间 | 清洗环节耗时下降 ≥50% | 工具内操作时长埋点 + 首批用户访谈 |
| 报告撰写耗时 | 一份专题/复盘报告 4-8 小时 | 框架搭建+成文耗时下降 ≥60% | 构思模块使用前后自报工时对比 |
| 重复 SQL 复用率 | 常用 SQL 散落在个人文件，复用率低 | 相似分析场景 SQL 复用率 ≥40% | 片段库调用次数 / 新建查询次数 |
| 需求返工率 | 需求沟通偏差导致返工（业务方估测 20%+） | 因口径偏差导致的返工 <10% | 需求单状态标记"返工"的比例 |

> 注：基线数据为行业普遍经验值，产品上线后以首批 5-10 名种子用户的实测数据校准。

### 1.5 应用场景

产品覆盖数据运营岗位的典型工作场景（按出现频率排序）：日常数据监控与异常预警、活动效果评估与复盘、用户行为路径/漏斗分析、渠道效果评估与预算优化、用户画像与分层、留存与流失分析、A/B 测试与实验分析、专题分析报告、预测建模与目标制定。

以上场景的共同特征是：**数据来源杂、清洗量大、分析框架可复用、报告产出重**——正是 BI 工具不承接、而数据运营每天都在做的工作。

## 2. 需求概述

### 2.1 用户痛点（已排除 BI 软件可解决的内容）

- **P1 数据分散，找数取数成本高**：数据散落在 Excel/CSV、多个业务库导出文件、同事共享文件中；每次分析前要手动收集、辨认字段含义，重复劳动严重。
- **P2 数据质量差，清洗全靠手工**：缺失值、重复行、异常值、日期格式混乱、数字被存成文本……每份数据都要在 Excel 里重复清洗，无沉淀、无标准、无记录。
- **P3 需求沟通偏差，做完才发现做错**：业务方一句"拉个数"就开工，口径、维度、时间范围理解不一致，报告产出后返工，双方时间双浪费。
- **P4 相似分析重复造轮子**：留存、漏斗、复购等分析框架高度雷同，但 SQL 片段散落在个人聊天记录/文档里，每次重写，且写法因人而异、质量参差。
- **P5 分析产出堆砌，报告不成形**：数据和图表都有了，但组织成一份结构清晰、语言专业的报告耗时巨大；新人尤其不知道报告框架怎么搭。
- **P6 工具与方法缺乏传承**：内部数据工具怎么用、指标口径是什么、踩过什么坑，全靠口口相传；新人上手慢，老人离职知识流失。

### 2.2 业务价值

- **对个人**：把数据运营从"取数工具人"中解放出来，单次需求交付周期缩短，产出质量稳定，把时间投向分析判断本身。
- **对团队**：SQL 片段、分析框架、工具知识从"个人资产"变为"团队资产"，新人上手周期从数周缩短到数天。
- **对业务方**：需求先确认框架再开工、紧急性可排序，数据需求的响应确定性和透明度显著提升。

### 2.3 版本范围

**V1.0（本版本）交付五大核心模块**——数据存储、轻度数据清洗、构思（AI 报告）、分析模板库、学习文档库——以及配套的需求 List 与紧急性排序能力。单用户本地优先 + 小团队局域网共享可用。

**明确不做（V1.0 边界）**：不做 BI 看板与可视化大屏、不做数据仓库建模与 ETL 调度、不做实时数据流接入、不做复杂统计建模（预测/LTV 模型仅提供框架模板，不提供建模引擎）、不做多角色权限体系。

## 3. 用户需求与功能需求

### 3.1 典型用户故事

| 编号 | 场景触发 | 用户期望 |
| --- | --- | --- |
| U1 | 业务方甩来一份 CSV 说"帮看看" | 导入后 1 分钟内看到字段编码、类型、前 5 行数据和体检报告，不用自己逐个翻表 |
| U2 | 每周重复清洗同类活动数据 | 把清洗流程保存成预设，下次一键套用，并知道本次清洗改动了多少行/多少字段 |
| U3 | 接到模糊的复盘需求 | 先在工具里选分析框架模板、填口径，导出框架给业务方确认后再动手，避免返工 |
| U4 | 又要写留存/漏斗分析 | 从片段库关键词搜到上次写好的 SQL，改表名字段直接跑，不重写 |
| U5 | 分析做完要交报告 | AI 根据数据结论自动搭报告框架、精炼语言，导出 Word/PDF 直接发出 |

**F6 全局**

| 优先级 | 功能点 |
| --- | --- |
| P0 | 模块间数据互通：存储模块的数据可被清洗、构思模块直接调用；清洗产物自动回写存储模块并标记来源 |

### 3.3 模块依赖关系

- **F1 是所有模块的数据底座**：F2、F3 均从 F1 选取数据文件，必须最先可用。
- **F2 依赖 F1**：清洗对象为 F1 中选定文件；清洗产物回写 F1。
- **F3 依赖 F1/F2**：报告引用的数据须来自已导入或已清洗文件；F3 与 F4 双向联动（报告中可插入 SQL 片段，分析中的 SQL 可沉淀进 F4）。
- **F5 相对独立**，可并行开发，仅依赖全局检索组件。

## 4. 业务流程

### 4.1 核心链路：一次临时数据需求的完整闭环

1. **需求录入（F3 需求 List）**：业务方提出需求 → 数据运营录入需求单（需求描述、需求方、截止时间、紧急性）→ 系统按排序规则（紧急性 × 截止时间 × 预计工时）输出优先级清单。
2. **框架先行、业务确认（F3）**：从框架模板库选择对应分析类型（复盘/漏斗/留存等），填写指标口径、维度、时间范围 → 生成"分析框架确认页"发给业务方确认 → 确认后开工（未确认的需求单标记为"待确认"，不计入排期）。
3. **找数取数（F1）**：导入 Excel/CSV 或连接数据库取数 → 系统自动识别编码与字段类型、展示前 5 行 → 数据资产目录中可检索历史同类文件。
4. **数据体检与清洗（F2）**：自动扫描生成体检报告 → 选择预制清洗流程或逐项配置清洗动作 → 预览清洗效果 → 执行 → 输出清洗后新文件 + 数据变更统计，产物自动回写 F1。
5. **分析执行（F4 + 外部）**：从 SQL 片段库检索复用常用查询（留存/漏斗/TopN 等），参数化改表名与日期；复杂分析可在用户熟悉的外部工具（Excel/BI/Notebook）中完成，结论数字回填报告。
6. **AI 辅助成稿（F3）**：在报告编写区按已确认框架组织内容，引用数据文件中的关键数字 → AI 自动构架/补全框架、精炼语言 → 人工校验数据与结论 → 导出 Word/PDF。
7. **交付与沉淀**：报告交付业务方 → 本次可复用的 SQL 片段保存进 F4、清洗流程保存为预设、相关文档上传 F5 → 需求单标记完成并记录实际工时。

### 4.2 异常流程

- **文件导入失败（编码损坏/超大文件/格式不支持）**：提示具体原因（如"文件编码非 UTF-8/GBK，已尝试自动转码"）；超过行数上限时提示分批导入或连接数据库；不支持的格式给出支持清单。
- **数据库连接失败**：区分提示：网络不通 / 凭据错误 / 只读权限不足；连接配置支持测试连接；失败不影响文件类功能。
- **清洗动作导致数据异常（如类型转换丢值）**：每个清洗动作执行前显示影响行数预览；转换可能丢失数据时二次确认；所有操作可一键回滚到清洗前快照。
- **AI 报告生成失败或内容失真**：AI 服务超时/失败时保留用户已写内容，可重试；AI 生成的所有数字结论必须标注来源数据文件与字段，无来源的数字不允许写入报告（防幻觉硬约束）。
- **业务方退回框架确认**：需求单回到"待修改"状态，保留确认意见批注；框架修改后重新发起确认，版本可追溯。

### 4.3 关键状态流转

| 对象 | 状态机 |
| --- | --- |
| 需求单 | 待确认 → 已确认/排期中 → 进行中 → 已交付；分支：返工中（退回后回到进行中）、已取消 |
| 数据文件 | 已导入 → 体检完成 → 清洗中 → 清洗完成（产物已回写） |
| 报告 | 草稿 → AI 已生成/待校验 → 已校验导出 |

## 6. 功能详细设计

### 6.1 F1 数据存储模块

**界面结构**

- **左侧目录树**：两级分类——"按文件类型"（Excel / CSV / 数据库表 / 清洗产物）与"我的分类"（用户自建文件夹+标签，两种视图可切换）。
- **文件列表区**：文件名、来源类型、行数/列数、导入时间、标签、关联需求单；支持搜索（文件名/字段名/备注全文检索）。
- **数据预览页（点击文件进入）**：顶部为元信息条（编码、行列数、大小、来源、导入人）；中部为字段卡片列表——每个字段显示字段名、推断类型（文本/整数/小数/日期/布尔，类型可手动修正）、缺失率、示例值；下方为前 5 行数据表格。

**关键规则**

- 导入时自动检测编码（UTF-8 / GBK / GB2312 依次尝试），检测结果在元信息条展示，识别错误可手动切换后重新解析。
- 类型推断规则：日期格式字符串（如 2026/9/1、2026-09-01 12:00）提示"疑似日期"；数字列中混入文本标记为"混合类型"；同一列缺失率 >50% 给出警告色。
- 原始文件只读，任何处理产物均为新文件，命名规则 `原文件名_cleaned_YYYYMMDD_HHMM`。
- 数据库连接仅允许只读账号，连接配置本地加密存储；取数结果落地为本地文件后进入统一目录。

### 6.2 F2 轻度数据清洗模块

**数据体检报告内容**

| 体检项 | 检测内容 | 呈现方式 |
| --- | --- | --- |
| 缺失值 | 各字段缺失率（空值/空字符串/NA 类文本统一识别） | 字段卡片缺失率进度条，>20% 红色预警 |
| 重复行 | 完全重复行数；按主键/指定列重复行数 | 顶部汇总数字 + 重复明细预览 |
| 异常值 | 数值列超出正常范围（如年龄 <0 或 >120、金额为负），采用规则阈值 + 3σ 统计双策略 | 异常值清单 + 疑似规则说明，用户确认后才标记 |
| 格式不符 | 日期格式混乱（斜杠/横杠/中文混用）、手机号/身份证位数异常、文本前后空格 | 问题样例逐条列出 |
| 类型误判 | 应为数字却存为文本（如 "1,234" 带千分位）、应日期却为文本 | 给出"建议转换类型"操作按钮 |

**清洗交互逻辑**

1. 从 F1 选定文件 → 点击"开始体检"，扫描完成后展示体检报告。
2. 清洗配置区：左侧为可添加的清洗动作列表（缺失值填充/剔除、去重、类型转换、日期标准化、字符串修剪、筛选过滤、字段重命名/删除/排序），右侧为清洗流程编排区——动作按顺序排列，每个动作可展开配置参数。
3. 每个动作支持"在样本上预览效果"（显示影响行数与前后对比样例）；可能造成数据丢失的动作（删行/删列）需勾选确认。
4. 流程编排完成后可保存为预设（命名+适用场景描述，如"活动订单数据标准清洗"）；下次清洗时在预设列表选择套用，可再微调。
5. 执行清洗 → 生成新文件回写 F1 → 弹出数据变更统计：处理缺失 X 处、去重 Y 行、类型转换 Z 个字段、剔除异常行 W 行，统计随文件永久保存可回看。

### 6.3 F3 构思模块（AI 报告 + 需求管理）

**功能一：报告编写区**

- 框架模板库内置 7 类常见数据分析报告骨架：**活动复盘报告、漏斗/路径分析报告、留存流失分析、渠道效果评估、异常分析报告、A/B 测试报告、专题分析报告**；每个模板预置标准章节（背景 → 口径 → 数据表现 → 归因 → 结论建议 → 附录）与提示语，一键插入文档。
- 文档编辑器支持标题/列表/表格/图片粘贴；可通过"引用数据"按钮插入 F1/F2 中文件的关键数字，引用以卡片形式标记来源文件与字段。
- AI 环节分两步：①**构架**——根据用户填写的需求描述与所选模板，生成/补全报告章节框架（各章节标题+写作要点）；②**精炼**——对选中段落或全文做语言专业化、结构化改写，保留全部数字与事实。
- **防幻觉硬约束**：AI 输出中的数字若无法匹配到用户引用的数据源，标红提示"无数据来源"，不允许进入导出稿；导出前强制展示"数据引用核对清单"。
- 导出 Word（.docx）与 PDF 两种格式，模板化排版（封面标题、目录、页眉）。

**功能二：需求 List 与排序**

- 需求单字段：标题、需求方、需求描述、提交时间、期望截止时间、紧急性（高/中/低，由需求方或运营标记）、预计工时、关联分析类型。
- 排序规则透明可调：默认按得分 = 紧急性权重 ×0.5 + 截止紧迫度 ×0.3 + 业务方权重 ×0.2 降序，权重在设置页可调整；清单支持拖拽手动覆盖。
- 每个需求单可生成"分析框架确认页"（单页摘要：分析目标、指标口径、维度、时间范围、交付物与时间），一键复制链接/导出 PDF 发给业务方；确认状态回写需求单。

### 6.4 F4 分析模板库（SQL 片段库）

- 片段条目字段：标题、业务场景分类（留存/漏斗/TopN/同环比/去重/汇总/其他）、SQL 正文、注释说明、数据库方言标签、来源（手动录入/从分析中沉淀）、使用次数。
- 录入方式：用户手动新建粘贴；在构思/分析过程中选中 SQL 一键"存为片段"。
- 检索：关键字匹配标题/正文/注释/分类；支持按方言、分类筛选；检索结果高亮关键字，提供"复制"与"插入到报告"两个动作。
- V1.0 内置 10 条高频种子片段：**次日留存、7 日留存矩阵、漏斗转化率、分组 TopN、连续 N 天行为、同环比、去重 UV、累计值、中位数、复购率**，帮助用户理解用法。

### 6.5 F5 学习文档库

**核心度量指标**

- 清洗提效率 = 使用预设完成的清洗次数 / 总清洗次数；目标 ≥50%。
- SQL 复用率 = 片段复制/插入次数 /（新建查询次数+片段使用次数）；目标 ≥40%。
- AI 采纳率 = AI 生成内容被保留的段落数 / AI 生成总段落数；无来源数字拦截次数单独监控（目标：导出稿无来源数字 = 0）。
- 需求返工率 = 标记返工的需求单数 / 已交付需求单数；目标 <10%。
- 周活跃留存：种子用户次周留存 ≥70%（工具类产品黏性参考）。

### 9.2 边界条件

- **业务边界**：仅服务数据分析/运营场景的文档与表格处理；不承接业务系统交易数据写入；不替代正式数仓的指标口径治理。
- **技术边界**：单文件 500MB / 100 万行；AI 单次处理文本 ≤2 万字（超出分章节处理）；数据库仅支持 MySQL / PostgreSQL 只读连接。
- **数据边界**：工具内不产生新的业务事实数据，所有分析结论均可回溯到导入文件；清洗不覆盖原始数据。
